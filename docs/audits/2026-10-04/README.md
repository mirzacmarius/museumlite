# MuseumLite application audit

Date: 4 October 2026. Status: analysis complete; implementation awaits explicit batch approval.

MuseumLite already contains substantial museum operations functionality. Its main weaknesses are inconsistent authorization at batch boundaries, destructive treatment of permanent evidence, and disconnected custody and workflow state. Improving those foundations will make the existing modules more useful than adding more independent screens.

## Scope and evidence

This is a repository-wide architecture and product audit with targeted deep tracing of shared boundaries and multi-module workflows. It is not a claim that every line of every file was manually reviewed or that every production configuration was tested. The schema and routes were inventoried; shared authorization, lifecycle, movement, public projections, imports, reporting, notifications, and representative screens/forms were inspected. Module findings below distinguish demonstrated defects, source-visible behavior, product gaps, and unverified runtime concerns.

The agreed product scope is museums first, with optional library circulation. Existing institutional records are permanent. Migrations should be additive and preserve identifiers, evidence, and history. Spectrum 5.1 is a workflow reference, not an assertion of certification or jurisdiction-specific compliance. The [Collections Trust procedure list](https://collectionstrust.org.uk/spectrum/procedures/) provided the reference for coverage; the installed Next.js 16.2 documentation and `convex/_generated/ai/guidelines.md` provided framework guidance.

The audit used the invoked grilling and domain-modeling skills. The accepted decisions are museums first, optional library circulation, permanent institutional records, explicit per-file public approval/renditions, archival withdrawal with restore, and preservation of environmental ingestion using device credentials. The user described temperature/humidity webhooks and subsequently said they plan to use Tuya sensors. Exact devices, gateway, current live status, payload contract and supported authentication remain unverified; the preservation requirement remains in force for any existing sender. Broader domain redesigns below are proposals, not silently accepted ADRs.

No application code, schema, migration, permission configuration, or live record was changed. Only this audit directory was created. Temporary probes lived outside the repository and used `convex-test` in memory. No Convex deployment or cloud write was performed. A concurrent change to `CLAUDE.md` was left untouched.

## Architecture assessment

The Turborepo separates main Next.js UI, marketing/public UI, Convex backend, shared UI, email, analytics, logging, and TypeScript tooling. Convex owns data, auth, storage, background work, and transactional operations. Next.js uses `src/proxy.ts`, server layouts/pages, client reactive queries, and reusable form/table controls. This is a sound overall allocation; a platform rewrite is not warranted.

The shared permission helpers derive the actor from Convex Auth and inspect organization membership and role grants. Organization query/mutation wrappers and library permission wrappers are useful foundations. Normal write paths often verify referenced organizations, but alternate bulk and media paths do not consistently reuse those guarantees. Feature, module, permission, and site concepts are implemented but do not yet form one consistent policy vocabulary.

The backend has useful domain helpers for loan transitions, exhibition workflows, collection lifecycles, numbering, document publication, counters, and transfer registries. The next architectural step is deeper domain commands that own invariants and history together, rather than additional generic CRUD layers. A full event-sourced rewrite is unnecessary: transactional commands plus append-only operational events can coexist with the current schema.

## Decision and confidence boundaries

The most consequential recommendations are redesigns of custody, condition checks, exhibition membership, provenance/parties, and entry/exit. They require accepted domain definitions and migration fixtures before implementation. Smaller authorization fixes should proceed in the first approved batch without waiting for the broader product redesign.

The insurance frontend checks the conservation feature and its backend reads use loan permissions. Current feature requirements put both at Pro, so the code coupling is demonstrated, but an independently entitled insurance customer being denied access is not demonstrated. Treat this as policy clarification, not a proven billing exploit.

The accession draft schema lacks several direct-catalog fields. That is a capture/parity gap that can cause later re-entry; the audit does not claim that those absent draft fields are currently accepted and then silently discarded. Loan history may help manually reconstruct a former location, even though dispatch clears the structured current location and return does not automatically restore it.

The browser showed divergent overview versus usage counters, plan labels, and exhibition metric/list counts. Exhibition status divergence is supported by source. Counter/billing discrepancies may include seeded or migration state; reconcile data and definitions before attributing them to a new billing defect. No claim about paid subscription ownership is made.
