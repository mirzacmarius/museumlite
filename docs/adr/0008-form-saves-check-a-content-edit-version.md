# Form saves check a content edit version; unsaved input is kept on the device

A form that edits one record reads the record's edit version from `recordEdits.getEditState` and sends it back as `expectedEditVersion`. The server refuses a save made from an older version with the coded `EDIT_CONFLICT`, and returns the new version after a save. The version is a digest of the values that form edits (for an Object, its catalog fields and Collection group memberships; for an intake draft, the draft and its files; for a loan, its terms and party), not a stored counter. So every writer that changes one of those values outdates open forms (a move, a Party replacement in the Parties panel) without having to remember to bump anything, while writes to other fields and saves that change nothing leave colleagues' forms current. The whole form is checked, not each field: a stale save is refused even when the colleague changed a different field, and the form then offers to keep the staff member's changes on the latest version, so nobody's edit is silently overwritten or silently merged.

Input that has not been saved is kept only in the browser's local storage, under the staff member and Organization, for at most a week, and is cleared on save, discard and sign-out. It is offered back after a reload, an expired session or a crash, never restored without asking, and checked against the record's current version like any other input. We did not add server-side autosave drafts for catalog records: Objects and Cases are institutional records (ADR 0002), and half-finished edits would need their own permissions, retention and review. The cost is that recovery does not follow staff to another device, and files chosen but not yet uploaded cannot be recovered.
